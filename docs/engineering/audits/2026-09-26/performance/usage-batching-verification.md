## Acknowledgement and limits

Each caller retains an unresolved promise until its batch COMMIT is acknowledged. Events waiting in memory are not reported as durable. A process crash before acknowledgement can discard those pending events, just as an interrupted uncommitted transaction can; an acknowledged event is already in PostgreSQL. Business-response behavior remains unchanged: exhausted operational-metering errors are logged and do not replace a business response. This remains operational cost attribution, separate from the customer billing ledger.

The writer groups at most 64 events from one tenant, coalesces for 5 milliseconds, allows at most two active batches and retains at most 1,024 queued plus active events per process. Queue admission expires after 500 milliseconds. Pool checkout remains limited to 500 milliseconds, each transaction to 1.5 seconds, statements to 750 milliseconds and lock waits to 250 milliseconds. These are scheduling deadlines, not hard wall-clock limits under a stalled event loop. The configured usage-pool connection budget is unchanged. Round-robin tenant scheduling prevents one busy tenant from continually taking all queue slots available for dispatch.

Every transaction still uses `SET LOCAL ROLE atlas_app`, transaction-local tenant context, parameterized values, forced table RLS, and `ON CONFLICT (id) DO NOTHING`. No migration, privileged writer or cross-tenant insert bypass is introduced. A batch-level database failure rejects every member. A lost COMMIT response can be retried once with the original event IDs after a 25-millisecond delay; the journal deduplicates replay. Queue admission failures are not immediately retried because no ambiguous database commit needs resolution. Graceful shutdown first stops producers and calls `flushTenantUsageMeter`, which waits through the full recorder lifetime including retry delays and terminal diagnostics, then closes the pool. Closing the global pool is terminal for the process: a late retry is rejected and cannot recreate it. The production recorder is process-global so a flush after module reload still sees earlier pending retries.

The transaction still uses five commands, now per batch. Full 64-event batches therefore reduce transaction and insert count by a factor of 64, but actual improvement depends on arrival concurrency and the runtime. Sparse traffic pays the additional 5-millisecond coalescing interval.
