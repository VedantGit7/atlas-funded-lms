# Member erasure (launch plan 5.7, part 2)

Status: implemented on `feat/member-erasure`, 18 November 2026. Replaces the F14 "access removal only" outcome (`f14-privacy-lifecycle-remediation.md`) with real erasure of a member's personal data in one academy, following the owner's decisions of 18 November 2026 and the published Privacy Policy ("deletion within 30 days").

## What happens to a member's data

The membership row stays as an anonymised tombstone, so the records the academy keeps still point at something ("Deleted member"), and foreign keys (all `RESTRICT`) stay valid.

## Who runs it, and when

1. A deletion request is made by the learner (profile → privacy) or an admin. It is scheduled **7 days** ahead, well inside the 30 days the Privacy Policy promises.
2. An admin may **process** it early; that only brings the schedule forward to now.
3. The **worker** erases due requests (task `member-erasure`, each sweep, a few per academy at a time). Only the worker can: `member_erasures` accepts inserts from `atlas_worker` alone, and that row is what unlocks the append-only tables (below).
4. Database work commits in one tenant transaction. Then the worker deletes the stored files and, if eligible, the login account, and marks the request `SUCCEEDED` with a versioned outcome (`version: 2`, `operation: "erase_member"`). A failure after the commit leaves the request `RUNNING`; the next sweep resumes from the recorded erasure.

## Append-only tables

Several tables are append-only evidence, enforced by `app.reject_update_delete()` triggers (and, for `proctoring_events`, revoked grants). Erasure needs to delete or redact rows in them. The trigger now allows exactly two things, and only while the current transaction has an open row in `member_erasures` for that academy:

- `DELETE` of a row (the erasure's own deletes);
- on `audit_entries` and `outbox_events`, an `UPDATE` that changes nothing but the JSON payload columns to `{"redacted": true}`.

Everything else stays refused, for every role. An application-plane bug or injected SQL can't open the door, because `atlas_app` can't insert into `member_erasures`, and every use of the door is permanently recorded there.

## Audit chain

`audit_entries.entry_hash` covers the SHA-256 of each JSON payload. Before a payload is redacted, the trigger stores the original payload hashes in `audit_entry_redactions`; `app.verify_audit_chain()` uses those stored hashes for redacted entries. So the chain still proves no entry was added, removed or reordered, and that a redaction (and only a redaction) happened to a payload. Columns that are hashed directly (actor and target IDs, `ip_hash`, `user_agent_hash`) are left as they are: the IDs point at the tombstone, and the two hashes are salted.

## Backups

Coolify keeps backups for 14 days. `member_erasures` is the durable list of completed erasures; a restore must re-run them before the restored database is reopened (`docs/runbooks/privacy-lifecycle.md`, "After a restore").
