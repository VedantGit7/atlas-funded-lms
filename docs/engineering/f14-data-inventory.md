# F14 — Privacy data inventory and policy evidence

Reviewed 20 September 2026 from repository source; retention enforcement was rechecked after F15/F22 on 26 September 2026. This is an engineering inventory, not a statutory retention schedule or a legal-compliance determination. No live database, provider console, secret values, or production backup configuration was inspected for this inventory. Table names below are physical database names from `backend/prisma/schema.prisma`, with SQL-only replay registries identified separately. JSON/text fields and copied artifacts require content-aware review; a membership foreign key alone is not a complete discovery strategy.

## Policy evidence and unresolved decisions

The repository contains implemented retention settings for proctoring media, attribution events, replay records, and report/export file governance. Those settings establish current software behavior; they are not evidence of an approved organization-wide retention policy. No approved per-domain retention schedule, legal-hold registry, hold authority/release procedure, or hold checks in the existing purge functions was found in the reviewed docs, Prisma schema, migrations, and application code.

The help-center text previously said billing/certificates could be retained in anonymized or legal-hold form. That statement does not establish that either operation exists. The architecture/build documents and F14 finding ask for lifecycle work, but do not supply approved durations. `APPROVED_EXPORT_DOMAINS` is a code allowlist, not policy approval for retention or a promise of complete personal-data portability.

Before implementing wider deletion/anonymization, the privacy/product owner must record, for each category below: purpose and authorized scope; retention trigger and duration; deletion versus anonymization versus retention; exception/hold authority and review date; provider and backup treatment; and evidence required to close a request. No new durations are proposed here. Existing production tenant choices, processor contracts, and backup windows remain unknown.

## Identity and isolation boundaries

- Global identity: `auth_principals` holds the unique Supabase user ID, unique email/normalized email, MFA flag, status and login timestamps. It has no `tenant_id`. `platform_operators` holds global operator grants/revocations and principal references. Supabase Auth is a separate identity store outside this schema.
- Tenant identity: `memberships` links `tenant_id` to optional `auth_principal_id`, and includes invitation email/token hash, invitation expiry, status and activity timestamps. `(tenant_id, auth_principal_id)` is unique; a principal can belong to multiple tenants. Invitation-only rows may have no global principal. `member_profiles`, preferences and most activity tables use the tenant membership ID.
- Membership access removal must not delete a global principal, revoke unrelated tenant memberships, or imply global account deletion. Global erasure needs independently authorized identity resolution and a check of other tenant and platform relationships.
- Retained actor/request/subject IDs in audit records, events, report payloads and provider identifiers can remain linkable. Hashing a stable identifier is not evidence that its data is anonymous.

The default outbox processors enumerate only tenants with `state = 'ACTIVE'` and `deleted_at IS NULL`. F15 export-file cleanup and F22 usage draining separately enumerate all tenants, including inactive/deleted tenants. Tenant replay, proctoring-media and attribution retention remain active-only. Extending those destructive tasks requires an approved scope and hold handling; this review did not broaden them. Source wiring is not proof the production worker runs or that backlogs are drained. No existing retention purge above checks a legal hold; do not describe held records as protected by a technical hold system.

F22 also retains processed usage-journal IDs for 30 days while leaving pending events intact, including for inactive tenants. This is an operational replay/metering setting, not an approved cross-domain schedule. Abandoned/superseded SCORM generation prefixes still need reference-aware cleanup; age alone is not sufficient because a currently published package can be old.

## Export/offboarding boundaries

The pre-F14 export snapshot selects only membership ID/status/joined time; profile membership ID/display name; non-deleted course ID/slug/title/status; and enrollment ID/course/membership/status. It omits other profile fields, global email/Auth data, most learner records and all provider/backup data. It is a limited tenant snapshot, not complete portability for one person. Its entitlement gate is a product export gate; a separate subject-access fulfillment process has not been established by that feature.

The existing membership processor calls `removeMember`, which changes `memberships.status` to `REMOVED`, sets `removed_at`, and records audit/outbox events. It does not erase/anonymize data, delete uploads or remove the global Auth identity. F14 completion descriptions must report that actual operation and list remaining scope. Historical success rows without detailed execution evidence cannot be retroactively presented as completed erasure.

## Follow-up acceptance criteria

1. Record approved policy decisions and authority per category; attach evidence of actual tenant/provider/backup configuration. Until then, label broader erasure and legal-hold fulfillment as unresolved.
2. Build an explicit subject-to-record/object map, including contact-only rows, free text, JSON snapshots and derived projections. Test tenant boundaries and principals shared by multiple tenants.
3. Make each approved erasure/anonymization operation resumable and auditable, with per-domain outcomes and provider object-deletion receipts. A failure or retained domain must remain visible; access removal alone cannot close a full erasure request.
4. Add hold creation/release/audit semantics and apply them to every affected purge before promising technical holds. Record retained categories/reasons and review dates without inventing retention periods.
5. Verify F15's separated file/link expiry and confirmed object cleanup on real configured storage. Resolve proctoring storage identity/absence checks, enforce approved run-record policies, decide and implement the remaining inactive-tenant scope, and verify workers/alerts. Do not treat the locally implemented export cleanup as full-domain retention closure.
6. Add complete subject exports only after scope/authorization decisions; include a machine-readable manifest of included/omitted categories and safe handling of other people's data.
