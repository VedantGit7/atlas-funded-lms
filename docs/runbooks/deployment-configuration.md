# Deployment configuration contract (F05)

The API, web server and outbox worker validate configuration before accepting work. Both Next.js Node instrumentation hooks validate before loading server monitoring; the worker validates before opening its health server. Invalid settings abort startup. The configuration checker is read-only and never connects to providers.

## Environment and preflight

F22 requires `ATLAS_SERVICE_RUNTIME=managed-node` on deployed API and worker services. Web remains on Vercel. See the [managed Node runtime contract](managed-node-runtime.md). Include the independent `USAGE_DATABASE_POOL_MAX` pool (default 2) in the cross-process database connection budget.

Inject settings from the deployment secret manager, then run each service check in that environment:

```sh
pnpm check:deployment api
pnpm check:deployment web
pnpm check:deployment worker
```

These commands use the existing process environment; they do not automatically load `.env.local`. For a local development check using that file:

```sh
node --env-file=.env.local node_modules/tsx/dist/cli.mjs --tsconfig backend/apps/api/tsconfig.json scripts/validate-deployment.ts api
```

Success prints `ok: true` and `connectivityVerified: false`. Check that the intended deployed environment is reported. Failure exits nonzero and prints variable names and safe reasons, without credential values. Do not log secret-manager exports or full connection strings.

`NODE_ENV=production`, `APP_ENV`/`RELEASE_ENV` production or staging, `VERCEL=1`, and Vercel production/preview indicators all activate deployed validation. In those runtimes `APP_ENV` must explicitly be `production` or `staging`. Production Vercel/release labels require `APP_ENV=production`; previews normally use `APP_ENV=staging` and isolated staging resources. A dev/test label cannot turn off deployed checks. Without deployment signals, local development/test can retain mock email and local storage. A production build run on a laptop also activates the deployed contract; use development mode for the local mock setup.

All three services currently share the contract because web-side handlers and the worker consume the same infrastructure. Build environments that execute server instrumentation must have the required configuration too. Supply public `NEXT_PUBLIC_*` settings at build time as well as runtime. Never put server credentials in public variables.

## Required deployed settings

| Area               | Configuration and constraints                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Persistent storage | `STORAGE_PROVIDER=r2`; explicit `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`. Optional `R2_PUBLIC_ENDPOINT` uses HTTPS. Storage schema validates size/TTL settings; signed TTLs are 60–900 seconds. Local providers and an explicitly supplied development signing secret are rejected. Leave unused `STORAGE_LOCAL_SIGNING_SECRET` unset.                                                                                                                                                                                                                                     |
| Shared rate limits | Redis and trusted-proxy settings from [the F04 runbook](rate-limiting.md). No memory fallback in deployed runtimes. Use an isolated staging Redis namespace/database and restrict direct origin access.                                                                                                                                                                                                                                                                                                                                                                                                         |
| Database           | `DATABASE_URL` and `PLATFORM_DATABASE_URL` with separate explicit runtime usernames, passwords and databases. Known owner/group logins are rejected, including `postgres`, `atlas`, `atlas_app`, `atlas_platform`, `supabase_admin`. Pooler usernames can include a project suffix. Require explicit `sslmode=require`, `verify-ca` or `verify-full`; prefer `verify-full`. Only `sslmode`, `schema`, `pgbouncer`, `connection_limit`, `pool_timeout` query keys are accepted, each once. Pool maximums must be positive integers no greater than 1,000. Migration credentials must not be runtime credentials. |
| Origins            | HTTPS origin `APP_URL`; hostname-only `PLATFORM_HOST`; explicit `API_INTERNAL_URL` origin. Internal HTTP is allowed only for loopback or `.internal` service names. Optional `PUBLIC_SITE_URL`/`CERTIFICATE_PUBLIC_BASE_URL` must be HTTPS origins. Restrict private networking separately.                                                                                                                                                                                                                                                                                                                     |
| Authentication     | `NEXT_PUBLIC_SUPABASE_URL`, public `NEXT_PUBLIC_SUPABASE_ANON_KEY`, server-only `SUPABASE_SERVICE_ROLE_KEY`. Public key must be publishable or a legacy anon JWT; secret/service-role keys are rejected there. If present, `SUPABASE_URL` must match the public URL. Key syntax is checked; validity and project ownership require live verification.                                                                                                                                                                                                                                                           |
| Secrets            | Distinct `CRON_SECRET` and `INTERNAL_WORKER_SECRET`, plus `OBSERVABILITY_HASH_SALT`, each at least 32 characters and without trivial/development values. `LEARNER_BILLING_ENC_KEY` must encode exactly 32 bytes in base64. Generate independent random values through the secret manager.                                                                                                                                                                                                                                                                                                                       |
| Email              | `NOTIFICATION_EMAIL_PROVIDER=smtp`, `SMTP_HOST`, valid `SMTP_PORT` (default 587), `SMTP_USER`, `SMTP_PASSWORD`, `NOTIFICATION_EMAIL_FROM`. SMTP uses implicit TLS on 465 and requires STARTTLS otherwise. Web and API/worker now use the same implementation.                                                                                                                                                                                                                                                                                                                                                   |
| Monitoring         | HTTPS Sentry DSN in `NEXT_PUBLIC_SENTRY_DSN` or `SENTRY_DSN`; `RELEASE_SHA` or `RELEASE_VERSION`; HTTPS `BETTER_STACK_WORKER_HEARTBEAT_URL`. Blank public DSN falls back to the server DSN. Optional trace sample rate is 0–1. Worker initializes server monitoring and pings heartbeat after successful sweeps, including an empty tenant list.                                                                                                                                                                                                                                                                |
| Worker             | Positive integer interval, batch limit, retries, health port and shutdown deadline; existing defaults apply when absent. Health port must be at most 65,535.                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Open Badge signing | Enabled by default. Require an Ed25519 `CERTIFICATE_ISSUER_PRIVATE_KEY`, `CERTIFICATE_ISSUER_DID` and HTTPS `CERTIFICATE_PUBLIC_BASE_URL`, or explicitly set `CERTIFICATE_OPEN_BADGE=false`. Certificate flags validated here must be exactly `true`/`false` if nonempty. Wallet/blockchain credentials and functionality need their own feature release checks.                                                                                                                                                                                                                                                |

The public-key distinction follows [Supabase's API key guidance](https://supabase.com/docs/guides/getting-started/api-keys). Never copy a service-role key into browser configuration to resolve a startup error.

F11 additionally requires `API_PROXY_SECRET` on web and API (not worker): at least 32 nontrivial characters, distinct from `CRON_SECRET` and `INTERNAL_WORKER_SECRET`, and shared only by web/API within the same environment. API ingress authenticates it before trusting forwarded tenant hosts. See the [deployment topology runbook](deployment-topology.md) for build-time API origin configuration, preview separation and rollout requirements.

The deployed **API** additionally requires `SCORM_CONTENT_SIGNING_KEYS`. These keys sign the per-launch SCORM package-read capabilities (see the [CSP runbook](content-security-policy.md#scorm-playback-audit-h2)).

- **Format:** `<kid>:<secret>` pairs, comma-separated, at most four. A kid is 1–16 characters of `[A-Za-z0-9_-]`. Each secret is at least 32 nontrivial characters. Every secret must differ from every other service secret.
- **Signing and verifying:** the first key signs; every listed key verifies.
- **Rotation:** prepend a new key and deploy. Wait out the six-hour capability lifetime, then remove the old key.
- **Scope:** web and worker do not need it.
- **Local development:** without it, local development uses a random per-process key, so open lessons stop loading their remaining files after an API restart until they are reopened.

Deployed **web** also requires `CSP_ENFORCE=1` (audit H5). Report-only is accepted only with `CSP_REPORT_ONLY_INCIDENT` set to an incident reference (3 to 64 characters of `[A-Za-z0-9_.:/-]`). That is the emergency rollback described in the [CSP runbook](content-security-policy.md), and it must be removed when the incident closes.

Deployed **web** additionally requires explicit client-IP attribution: positive `TRUSTED_PROXY_HOPS` or a valid `TRUSTED_CLIENT_IP_HEADER`. The default/template is zero trusted hops, which intentionally fails deployed web validation until configured. API and worker need no edge attribution setting. Configuration validation cannot prove that an edge overwrites/appends the selected headers or blocks direct origin access; verify that separately. Public calls and browser API rewrites with absent/invalid attribution fail closed with retryable 503.

## Release verification before routing production traffic

1. Run preflight with the actual injected configuration for API, web and worker. Start a fresh instance of each. Confirm missing required settings stop the instance before readiness in an isolated staging rollout. Confirm the normal build/start path succeeds with complete settings.
2. Connect with each runtime database login. Inspect effective roles and memberships, verify `NOSUPERUSER`/`NOBYPASSRLS`, and confirm tenant isolation with seeded staging tenants. Check `pg_stat_ssl` for encrypted transport and inspect the driver's effective certificate-verification configuration. Username checks alone cannot establish grants, row policies or TLS connectivity.
3. Exercise shared Redis counters from separate app instances, then the documented outage behavior. Verify ingress overwrites the trusted client-IP header and blocks bypassing the edge.
4. Upload a uniquely named, disposable staging asset through the application using a test tenant. Record its checksum and object key. Stop/restart the writing process or replace its instance; retrieve through a fresh process and verify matching content. Clean up only that test asset. Also verify signed URL expiry, bucket permissions and browser CORS. A successful configuration check does not prove R2 persistence. Browser CORS must allow the `content-type` and `content-disposition` request headers on PUT; see [uploaded-files.md](uploaded-files.md).
5. Verify SMTP authentication/TLS and send a controlled test notification to an approved test recipient. Verify delivery, tenant attribution and retry behavior. Do not use real learner addresses for a canary.
6. Start the worker with a test outbox event, verify processing and readiness, then verify graceful shutdown. Confirm the external heartbeat arrives both with and without active tenants. Set an appropriate missed-heartbeat alert window. Confirm a controlled server/worker exception reaches Sentry with release identity and redacted context.
7. Verify canonical tenant/platform routing, sign-in, a protected API request, upload/download, and worker-backed delivery in staging. Release only after these checks pass. Keep the previous deployment available for rollback and preserve persistent objects/database data on rollback.

## Scope and recovery

The F05 local remediation adds configuration validation and regression coverage. It does not deploy infrastructure, create buckets/roles, rotate secrets, verify live provider connectivity, send email, prove restart persistence or configure alerts. Those checks remain release gates. On a startup failure, correct the named settings and restart; do not suppress deployment indicators, choose local storage, enable mock email or substitute an owner database login.
